# Why Structural Code Quality Matters for AI-Assisted Development

## The Problem

AI coding assistants are only as good as the codebase they work in. A well-structured
codebase makes agents fast, reliable, and safe to use. A structurally degraded codebase
makes them unpredictable — and, critically, the degradation is often invisible until
it's severe.

Comprehensity measures the structural properties that predict whether AI agents will
succeed or fail on a given codebase. The measurements are objective, the output is
human-readable, and your source code never leaves your machine.

---

## The Evidence

These findings are not theoretical.

**Multi-file coordination is the dominant predictor of agent failure** (Ganhotra, SWE-bench,
April 2025). Hard tasks involve ~11x more lines changed and 4x more code hunks than easy
ones; 55% require changes across multiple files vs. 3% of easy tasks. An agent scoped to a
task that actually requires cross-cutting changes will fail — not because it lacks capability,
but because the codebase structure obscures the true scope.

**Repository-level variation is large.** On SWE-bench Lite, agent solve rates vary
dramatically by repository. Flask scores 0% (lowest in the benchmark); Requests scores
83.3%. Both are Python, both are mature open-source projects. The gap is structural.

**AI-generated code introduces more issues than human code** (CodeRabbit, December 2025,
large-scale study). AI-generated PRs averaged ~11 issues vs. ~6 for human PRs:
- Logic and correctness issues: +75%
- Security vulnerabilities: +100–200%
- Code readability: +200%

The readability finding is particularly significant: AI-generated code is harder for humans
to review *and* harder for subsequent agents to reason about. Each generation of AI-assisted
development slightly increases the cognitive load on the next one.

**These patterns actively recur in AI-assisted codebases** (Columbia DAPLab, January 2026,
15+ production applications):
- Agents lose architectural context as codebases grow, editing wrong components or
  re-implementing existing functionality
- Agents duplicate code rather than abstracting shared functionality
- Agents misunderstand module boundaries and inject logic into the wrong layer

The failure modes below are not inherited from pre-AI development practices. They are
actively generated by AI-assisted development and self-reinforce as the codebase grows.

## The Failure Modes

Comprehensity detects and measures eight structural conditions that degrade AI agent
effectiveness. They are ordered by how strongly they self-reinforce.

### 1. Copy-Paste Architecture

When code is duplicated rather than abstracted, LLMs learn the copy-paste pattern as
the correct idiom and generate more copies. A bug fix, security patch, or behavior change
must be applied to every copy — some will be missed. Over time the copies diverge silently.

Comprehensity detects exact, normalized, and approximate clone blocks; identifies which
copies have drifted from their siblings; and calculates refactoring ROI (clone size ×
caller count × copy count) to prioritize extraction work.

### 2. Dead Code Accumulation

AI-assisted development generates code faster than it removes it. Dead functions, retired
feature flags, and unreferenced modules remain in the codebase and pollute the context
every agent works with. Agents hallucinate calls to dead symbols; tests appear to cover
code that is never invoked in production.

Comprehensity detects unreferenced symbols via LSP call hierarchy analysis, identifies
test-only symbols that aren't covered by production paths, and flags the high-value
intersection: code that is both duplicated and unreferenced.

### 3. Type Fog

AI-generated code prioritizes functionality over type precision. `Any` propagation in
Python, liberal `any` in TypeScript, raw types in Java — the pattern is consistent across
languages. Types are the contract between components. In a type-foggy codebase, an agent's
model of the API surface is unreliable, and it generates more type-foggy code.

Comprehensity surfaces type errors and missing annotations from LSP diagnostics at
codebase scale, enabling teams to track type coverage as a leading quality indicator.

### 4. Interface Surface Explosion

Without clear boundaries between public API and internal implementation, everything
becomes a potential entry point. Agents reach into internals directly, bypass lifecycle
management, and create hidden coupling to implementation details that were never intended
to be stable.

Comprehensity measures the gap between nominal public surface (all exported symbols) and
actual public surface (symbols with external callers) using LSP reference analysis.

### 5. Modularity Drift

Directory structure and package names define *nominal* module boundaries. Actual coupling
— which files genuinely depend on which — often tells a different story. When an agent
is scoped to "the auth module," it operates on the nominal boundary; if actual dependencies
sprawl across four other modules, its changes have unintended consequences.

Comprehensity applies Louvain community detection to the actual import graph to reveal
clusters that reflect how the code truly operates, independent of how it is organized on
disk. Divergence between declared boundaries and actual coupling clusters is a finding.

### 6. God Objects and Critical Path Fragility

Symbols with high fan-in *and* high fan-out — called from everywhere and themselves
depending on many things — are single points of failure. Agents preferentially reach
for widely-imported symbols, accelerating their accumulation of dependencies.

Comprehensity detects god object candidates via function-level call graph analysis and
calculates change blast radius (transitive dependent count) per symbol.

### 7. Layering Violations and Circular Dependencies

Circular imports and upward dependencies create coupling that resists both human and
AI-assisted refactoring: any attempt to change one end of a cycle forces simultaneous
change to the other. These are invisible in directory listings and show up only in
import graph analysis.

Comprehensity identifies strongly connected components, bidirectional module dependencies,
and upward imports between nominal architectural layers.

### 8. Naming Incoherence

LLMs use file names, directory names, and symbol names as primary signals for where to
find and add functionality. Mixed conventions, high abbreviation density, and generic
names (`utils`, `helpers`, `manager`) cause agents to make wrong predictions about code
location and generate new symbols that increase the incoherence.

Comprehensity measures naming convention consistency, identifier clarity, and the
coherence of naming within actual (L4) coupling clusters.

## Privacy and Security

### Your source code never leaves your machine

Analysis is split into two phases with a hard boundary between them.

```
Your machine                            Analysis server (optional)
────────────                            ──────────────────────────
Phase 0: detect languages and
         build configurations

Phase 1: parse source files
         build import graph
         detect duplicate code
  → produces blueprint.json
  → ZERO outbound network calls

You review blueprint.json
You decide whether to share it  ──────→ Phase 2: graph analysis,
                                                  scoring, insights
```

Phase 0 and Phase 1 run entirely on your machine and make no outbound network calls.
This is enforced by the test suite — a socket-blocking fixture catches any accidental
network access before code ships.

### What blueprint.json contains

The blueprint is a compact, human-readable summary you can open in any text editor
before sharing it anywhere. It contains:

- **Relative file paths** within the project (e.g., `src/main.py`) — no absolute paths
- **File sizes** in bytes
- **Import relationships** between files, identified by short opaque IDs (`f0`, `f1`, …)
- **External dependency names** (e.g., `numpy`, `os`) — no version pinning data
- **Build config metadata** — declared project name, version, and dependency names
  from `pyproject.toml`, `pom.xml`, `Cargo.toml`, `go.mod`, `package.json`, and similar
- **Clone block records** — file IDs, line ranges, and SHA-256 hashes; no source code
- **Symbol metadata** (if `--semantic` was used) — function and class names, call edges,
  diagnostic counts; no function bodies

Everything in the blueprint is information you would not hesitate to write on a whiteboard.

### Production-code focus

The blueprint excludes noise by design:

- **Test files** are present in the file inventory but their symbols are excluded from
  symbol extraction and LSP queries. Test helpers are not production dead code.
- **Generated code** (`*_pb2.py`, `*.pb.go`, `*.generated.ts`, `generated/`, etc.) is
  treated the same way — present in inventory, excluded from symbol analysis.
- **Build artifacts and caches** (`.venv/`, `node_modules/`, `__pycache__/`, etc.) are
  excluded entirely before any data is collected.

Classification is path-based and auditable. You can verify by inspection which files
are treated as test files and which as production code.

### Zero LLM exposure in Phase 0 and Phase 1

Phase 0 and Phase 1 contain no LLM calls and no AI inference of any kind. They are
deterministic analysis tools: parse the files, walk the import graph, hash the clone
blocks, write the blueprint. There is no mechanism by which your source code could
reach a language model during these phases — because no network calls are made at all.

LLM inference is used only in Phase 2, which runs on the analysis server and receives
only the blueprint. The blueprint contains no source code. The model sees file paths,
import relationships, and function names — the same information you would describe in
an architecture document.

### Language servers (optional `--semantic` mode)

When the `--semantic` flag is used, comprehensity starts a language server, asks it to
analyze your code the way your IDE would, and then shuts it down. All communication is
to `localhost` only — the language server is a child process on your own machine and
makes no outbound network calls.

The tool issues a fixed, auditable set of LSP requests: open file, find references,
get diagnostics. Only production source files are opened — test files are excluded from
LSP queries by path pattern.

For fully air-gapped or CI environments, language server use can be disabled entirely:

```toml
# ~/.comprehensity/config.toml
[extract]
semantic_enrichment = false
```

### The tools

Comprehensity uses tools your developers almost certainly already run:

- **[tree-sitter](https://tree-sitter.github.io/tree-sitter/)** — the same open-source
  parser that powers syntax highlighting in VS Code, Neovim, and most modern editors.
  Small precompiled wheels; no network calls at runtime.
- **Language servers** — the same servers your IDE uses for "Go to Definition" and
  "Find All References." Started locally; no outbound connections.
- **[treepeat](https://github.com/mdubinko/treepeat)** — a pure-Python clone detection
  library that compares syntax trees to find matching blocks. Runs as a local subprocess.

## What You Get

Running `extract-blueprint` on a codebase produces `blueprint.json` — a compact,
schema-versioned file that drives the Phase 2 analysis report. The report covers:

| Metric | Source |
|--------|--------|
| Fan-in / fan-out per file | Import adjacency list |
| Circular dependency cycles | Import graph (DFS) |
| Hub / god-object candidates | High fan-in + fan-out |
| Clone density per module | Clone blocks |
| Clone clusters (files sharing multiple clones) | Clone blocks |
| Module cohesion and instability (Martin metrics) | Louvain clustering |
| Domain concept labels per module | LLM inference on paths + import structure |

The blueprint itself is a standalone deliverable — you can build your own analysis on
top of it, import it into any tool that reads JSON, or simply review it manually.
The clone detection output is also available as a SARIF file compatible with VS Code,
GitHub Code Scanning, and any SARIF-aware tool.

## Inspecting the Code

The Phase 0 and Phase 1 source is public and auditable:

| File | What it does |
|------|-------------|
| `src/phase0.py` | Language detection, build manifest scanning, install guidance |
| `src/scan.py` | Directory traversal, orchestration |
| `src/import_analysis.py` | Tree-sitter import parsers, import resolution |
| `src/ts_parsers.py` | Symbol extractors (function and class names) |
| `src/blueprint_io.py` | LSP client, blueprint assembly |
| `src/blueprint.py` | Blueprint data model (Pydantic) |

The no-network enforcement is in `tests/conftest.py`. The socket-blocking fixture
intercepts any attempt to open a network connection and fails the test immediately —
it is not a policy, it is an automated check that runs on every commit.
